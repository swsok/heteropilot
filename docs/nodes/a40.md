# Node profile — the A40 node

*Read this only after `bash scripts/whichnode.sh` says `detected node : a40`.*

## Inventory (observed 2026-08-27/28)

64 cores, 503 GiB RAM, kernel 5.4.0-216-generic. **8 × NVIDIA A40**, driver
560.35.05, CUDA 12.8. No NPU of any kind.

Topology from `nvidia-smi topo -m` — this is what determines island structure:

- **NVLink pairs**: (0,1) (2,3) (4,5) (6,7), `NV4` each.
- **NUMA node 0**: GPUs 0–3, CPU affinity `0-15,32-47`.
- **NUMA node 1**: GPUs 4–7, CPU affinity `16-31,48-63`.
- Across nodes is `SYS` (PCIe + UPI). Within a node, non-paired GPUs are `NODE`.

A size-4 island therefore means GPUs {0,1,2,3} or {4,5,6,7} — two NVLink pairs
bridged over PCIe, which is what `experiments/configs/clusters/exp1-a40-tp-sweep.yaml`
and both P/D fixtures model.

> Measured, and counter-intuitive enough to state: for host↔GPU bulk transfers,
> spreading a group **across** both NUMA nodes beats packing it onto one (4 GPUs:
> 80.0 GB/s cross-node against 70.5 same-node). Two memory controllers beat one,
> and host buffers are not NUMA-bound so they land on both. An early single-trial
> run showed the opposite ordering; that was noise.
> `experiments/results/gpu_host_bandwidth.md`.

## Environments

- `.venv` — planner + analytical simulator. No device needed. Recreate per
  `CLAUDE.md` §Environment.
- `.venv-vllm` — CUDA profiling and real vLLM. torch 2.10.0+cu128, vLLM 0.19.0,
  8 GPUs visible.

**`python -m serving` shells out to a bare `python -m chakra`**, so the venv must be
on `PATH`, not merely invoked by full path:

```bash
export PYTHONPATH=$PWD && export PATH="$PWD/.venv/bin:$PATH"
```

Forgetting this fails inside the Chakra converter with a `CalledProcessError`, some
way into a run.

## What is measured here

`profiles/accelerators/a40.yaml` and `profiles/calibration/a40.yaml` (α 1.017 /
1.011) are measurements of this node. The GPU leg of the cross-vendor KV path was
measured here on 2026-08-27: sustained pinned D2H **25.71 GB/s** single stream,
**82.63 GB/s** across 8 GPUs — only 40 % of ideal, because the host path saturates
around 83 GB/s. Raw data `outputs/a40_profile/host_bandwidth.json`.

Two traps that will repeat if the measurement is redone:

- **Pageable D2H is allocator-bound, not link-bound.** `.cpu()` allocates a fresh
  destination per iteration and PyTorch's CPU allocator stops caching above ~16 MB,
  so the column peaks at 16 MB and drops ~4.5× above it. Read the pinned rows.
- **A single parallel trial is not reproducible.** Host buffer NUMA placement is
  fixed at allocation and uncontrolled; two runs disagreed by 38 % on the 4-GPU
  figure. Repeat over independent allocations and report the median plus spread.

## What cannot be done here

No NPU, so nothing RNGD or ATOM. `furiosa` imports are confined to
`experiments/scripts/`, and `pyproject.toml` sets `testpaths = ["tests"]`, so no NPU
code is imported at collection time — `pytest` is clean. The NPU-only scripts
(`profile_rngd.py`, `rngd_device_facts.py`, `rngd_collective_probe.py`,
`rebuild_rngd_bundle_from_edf.py`, `bench_furiosa_endpoint.py`) simply will not run;
that is expected, do not try to make them.
