*`WORK_ORDER_p2_regular_spec_evidence.md` STEP V3, the CPU half. Run 2026-09-16
on the **A40 node**; no GPU was used and nothing was deployed. The work order
requires this table to be **confirmed before any deployment**. Generated by
`experiments/p2_evidence/v3_select_candidates.py`; machine-readable in
`v3_candidates.json`.*

> **Read this before approving.** Two of the four groups do not do what the work
> order assumed. **P2's TPOT form is not measurable on the A40** — the per-point
> margin there is 0.37–1.63 %, so the band in which rules (a) and (c) can
> disagree on TPOT is at most 0.80 ms wide and the best available candidate
> decides by **0.3 ms**. The measurable P2 case is decided on **TTFT** instead,
> by 3.1 s. And **P3 exists only as `mix(...)` candidates** — 40 of them, zero
> single-island — so D40 applies and the chosen one must be re-simulated before
> it is deployed. P1 and P4 are clean.

## The fixture

`examples/service_specs/llama31-8b.yaml`, 300 requests, seed 42. TPOT SLO
**50 ms**, TTFT SLO **25 000 ms**. Its two CUDA islands are 4 + 4, which is

domain with `refuse`.

**RNGD candidates are out of this STEP**, as the work order directs — there is no
RNGD card on this node. That exclusion is not neutral and §4 says why.

### P3's margin headroom, and why it is in the table

Rule (c) leaves P3 feasible by **0.623 ms**:

```
predicted p99 TPOT  49.160141 ms
per-point margin    0.441010 %
robust              49.160141 x 1.00441010 = 49.376942 ms
headroom to the 50 ms SLO                   =  0.623058 ms
```

*(The approval named 0.55 ms; the computed figure is **0.6231 ms**. The table
carries the computed one.)*

**That headroom is smaller than the separation the verdict rests on**, so the
result has to be read against measurement repeatability, not on its own: rule (b)
is wrong by 8.009 ms if the hardware comes in under 50, but rule (c) is only
right by 0.623 ms. **V2's run-to-run p99 spread decides whether the second half
of that sentence means anything**, and the V3 result must be recorded with that
spread beside it (user instruction, 2026-09-16). If the spread exceeds ~0.6 ms,
V3 can report that (b) over-rejected and must report that (c)'s pass is inside
the noise.

Alternates, two per group, are in `v3_candidates.json` — the work order asks for
them in advance so a deployment failure (HANDOVER §2.7, KV allocation) does not
stall the run. Counts of usable candidates per group: P1 **8**, P2 **6**,
P3 **40**, P4 **10** (excluded).

### What each one settles

**P1** is the baseline: all four rules say feasible. If the hardware agrees, none
of the rules produced a false rejection here; if it does not, every rule is
optimistic together and the finding belongs to the simulator, not to any margin
policy. D40-clean (single island).

**P2** is the invention's core case — the candidate the unmargined rule passes and
the per-point rule catches. It is decided on **TTFT**: predicted p99 TTFT 24 064
against a 25 000 target passes unmargined, and the per-point TTFT margin pushes
it to 28 112, which does not. **A measurement can resolve 3.1 s.**

**P3** is the case the invention rescues: the global 18 % rejects it (49.16 ×
1.18 = 58.0 against a 50 ms target, an 8 ms overshoot) while the per-point margin
of 0.44 % leaves it at 49.38, feasible. **A measurement can resolve 8 ms.** If
the hardware comes in under 50 ms, the global rule excluded a candidate that
worked.

**P4** tests whether holding was warranted. Its operating point, **L = 186.9**, is
above the A40 domain's top measured point (170.56), so `refuse` declines to judge
it. See §3 — this group cannot embarrass the policy, and it is worth knowing why
before spending a deployment on it.

## 1. The A40 per-point margin is too small for a TPOT-decided P2

Across all 210 A40-only candidates the per-point TPOT margin runs **0.37 % to
1.63 %, median 0.57 %**. Rules (a) and (c) disagree on TPOT only when the
predicted p99 lands in `(50/(1+m), 50)`, which at the largest margin present is a
band **0.80 ms wide**. The candidates that actually fall in it are:

| candidate | m | predicted p99 TPOT | robust | overshoot |
| --- | ---: | ---: | ---: | ---: |
| `cuda-a40-node_a40a-tp4-dp1-s256-t8192` (single island) | 1.32 % | 49.40 | 50.0 | **0.0 ms** |
| `mix(a40a-tp4-dp1+a40b-tp4-dp1)-s256-t8192` | 0.79 % | 49.90 | 50.3 | **0.3 ms** |
| `mix(a40a-tp4-dp1+a40b-tp4-dp1)-s256-t2048` | 0.77 % | 49.72 | 50.1 | 0.1 ms |

**A deployment cannot confirm or refute a verdict that turns on 0.3 ms of p99
TPOT.** Run-to-run variation has not been measured on this node — V2's first run
will establish it — but 0.3 ms on a ~50 ms p99 is 0.6 %, and nothing in the
committed measurements is that repeatable. Selecting the TTFT-decided candidate
instead is not a workaround: it tests the same claim (per-point margin versus
none) on the metric where this hardware's domain actually carries a margin worth
applying.

## 2. P3 is `mix(...)`-only, and D40 applies

Forty candidates are rejected by the global 18 % and feasible per-point. **All
forty are `mix(...)`.** None is single-island.

D40 records that `EnvelopeCache` keys on a placement string that does not record
which island got which share, so two candidates differing only by mirroring
collapse to one cached entry — measured at **8.5 % apart on TTFT** for exactly
this shape of A40 pair. V3 compares a prediction against a measurement, so a
candidate whose cached prediction may belong to its mirror cannot be used as it
stands.

**Required before P3 is deployed:** re-simulate the chosen candidate on its own
and use that prediction, not the cached one. It is CPU work and needs no GPU. The
alternative — deploying against a possibly-mirrored prediction — would make a
disagreement uninterpretable, which is the one outcome V3 cannot afford.

**Done, 2026-09-16 — and D40 did not fire.** Both the P3 and the P2 candidates
were re-simulated with the cache disabled (`v3_resimulate.py`, raw in
`v3_resimulation.json`) and reproduced their cached metrics **byte-identically**,
worst |Δ| = 0.000000 % across p99/p95/p50 TPOT, p99 TTFT, served concurrency,
throughput, energy and tokens/J. So each prediction is that candidate's own and
V3 may use it. This does not close D40: the mirrors may still share the key, in
which case it is the mirror's cached value that is wrong, not this one's.

## 3. Holding costs nothing on this fixture

All **30** candidates that `refuse` holds as `outside_calibration_domain` are
**already rejected under rule (a), with no margin at all**. So on this fixture
the policy never withholds a candidate that would otherwise have been
recommended: every held candidate is one the unmargined simulator had already
ruled out.

The ten A40-only held candidates sit at **L = 172.4 to 197.9**, all above the
domain's top measured point at 170.56, with predicted p99 TPOT of **90 to
229 ms** against a 50 ms SLO.

**What P4 can therefore establish is narrow, and it is worth saying so before
spending a deployment slot on it.** The measurement will record what the hardware
does at an operating point nobody measured — which is useful for the domain — but
it cannot show that holding was wrong, because no rule wanted this candidate
anyway. The work order anticipated this ("실측 결과가 어느 쪽이든 '판단 근거
부족'이었음은 변하지 않으나, 실측값을 기록"). **P4 is the group to drop first if
GPU time is short.**

## 4. What the A40-only restriction costs

The RNGD-CARD domain's margin at the sweep's operating point is **~22 %**; the
A40's is **~1 %**. The cases where a per-point margin visibly changes a verdict
therefore live on RNGD, and this STEP cannot reach them. Concretely, the
disclosure's §5.6 candidate B — predicted 48.41 ms, robust 59.04 — is an RNGD
candidate, and nothing in the A40-only set reproduces that separation.

So V3 as scoped can show that the per-point rule **agrees with the hardware on
A40**, where it barely acts, and can show one TTFT case and one rescue case. It
cannot supply the §6 numbers for the regime the disclosure's example is drawn
from. That needs the RNGD node and is not scheduled.
